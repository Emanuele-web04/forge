Status: **Phases 0–3 done; the real-agent E2E test passed unassisted (2026-08-16).** Tier 1 works end to end: ghost cursor on a dedicated `synara-agent` seat (Phase 0 demo drove kcalc to a verified 78 × 6 = 468 while the user's pointer and keyboard stayed untouched), in-compositor capture from the plugin (window and region PNGs, both cursors excluded, verified pixel-correct against the live desktop), and the server backend running the whole path — supervision, reconnect, capture serialization, AT-SPI perception, provisioning across all nine providers. Phase 3a (web ComputerPanel, computer-control opt-in) and Phase 3b (idle timeout, release hotkey, smooth motion, panel input forwarding, thread-scoped events, AT-SPI semantic writes) are implemented and reviewed. The fourth E2E run completed the KCalc task end to end with no human help: a Claude Sonnet 5 thread launched the app, clicked out 12×34, read the result 408 from zoomed screenshots, and closed the window. Phase 4 (portability and hardening) is in progress; the run's one finding — occluded windows silently swallow coordinate clicks — was its first work item. As of 2026-08-19 the dedicated seat's one real limit is closed: applications that never bind a runtime seat (Chromium/Electron and everything behind Xwayland) are driven by writing straight to their own input resources, so Tier 1 on the human's desktop now reaches every application while the human's cursor and focus stay untouched — and the plugin installs itself into the user's home directory with no `sudo` and no toolchain, from binaries built per KWin version in CI. ## Current capabilities (authoritative — everything below this section is a build log, not a list of current limits)

Read this before reasoning from any dated entry further down. The entries below record how the feature was built, including earlier models that were later superseded ("an earlier draft said X, that was wrong" appears often). Do not reconstruct a limitation from them; the current truth is here.

- **Reach: every visible application on the human's real desktop, no restart ever required.** A client is driven on the dedicated `synara-agent` seat only when it provably has its `wl_pointer` object on that seat; every other client — Chromium, Electron, Xwayland, and Gecko (Firefox/Zen) alike — is driven by direct per-client injection (writing to the client's own `wl_pointer`/`wl_keyboard` resources), the universal macOS "post to the target" path, with the human's cursor untouched. An app that started before the agent seat existed is reachable too. The path is chosen by _where the client's pointer object lives_ (`PointerInterface::get(resource)->seat()`), not by whether it bound the seat's global — binding the global and creating a pointer on it are separate requests, and Gecko does the first without the second (it binds every seat but puts its pointer on seat0). A wrong guess can only route a client to direct injection, which works for any conformant client, so it never costs reach. `stateJson` reports `directInjection: true`. The plugin refuses only a client with no pointer/keyboard on any seat. Delivery over either path is exactly-once per event — one input resource, never every resource the client holds — and the keyboard is re-stamped onto the agent's target before every key, so the human clicking another window mid-type cannot pull the agent's remaining keystrokes into theirs. The pointer side keeps its own enter/leave bookkeeping per target surface, and the Hyprland plugin invalidates that enter whenever the human's seat enters or leaves any surface of the same client, so a click aimed at one window of a browser cannot be swallowed because the human is hovering the browser's other window.
- **The human is never disturbed:** the agent has its own seat and cursor; the real pointer, keyboard focus, and active window are untouched, and the human can work at the same time.
- **Minimum acceptance bar (stated by the user 2026-08-27; it is a floor, not a goal):** when a user asks an agent to use the computer, the agent spawns its own cursor and controls the computer just as if a person were doing it. The user sees it working **in the Synara app, and that is all they see**: no new windows pop up on their desktop, and anything the machinery needs — a nested compositor, a private bus, plugin installs — happens in the background. Visually it must read like watching someone else remote-control the computer. **Clarified by the user later the same day: "the computer" means their real desktop.** The agent controls the user's actual computer — their real applications, in the same environment the user works in — with its own separate cursor and inputs, exactly as Tier 1 does on KDE. An isolated nested desktop ("an entirely separate computer in a preview window") does **not** meet the bar; it is the floor, acceptable only on compositors that cannot host agent-seat code in-process (GNOME/Mutter, and anything else without a plugin system). On compositors that can — KWin (done) and **Hyprland** (plugin system confirmed viable 2026-08-27: 0.56.2 headers + `hyprpm` present, hello-world plugin compiles) — the bar is real-desktop control via an in-compositor plugin. Where the nested floor does apply it must run **headless** (`--virtual`) with the Computer pane as its only screen; a nested session that surfaces as a host window fails the bar outright (a black compositor window reads as a glitch, not a feature), and the windowed mode survives only as an explicit debugging opt-in (`SYNARA_COMPUTER_NESTED=window`), never a default.
- **Seat policy (decided 2026-08-26, authoritative over every Tier 2 entry below):** the agent **never** drives the seat the human is sitting at — that sentence is the success criteria, not a preference. The shared-seat portal backend (Tier 2 against the real desktop: portal RemoteDesktop, `zwlr` virtual devices, the native desktop helper, the shared-seat arbiter) was first disabled (2026-08-26: unreachable from `selectLinuxBackend`, `SYNARA_COMPUTER_BACKEND=portal` refused with the policy) and then **removed from the tree outright (2026-08-29)** — `apps/server/src/computer/portal/`, the native helper and its prebuild pipeline, the GNOME Shell extension, the arbiter, the consent RPC, and the `sharedSeat`/seat-health contract fields are gone, so nothing in the codebase can attach input to the human's `wl_seat`. `SYNARA_COMPUTER_BACKEND=portal` is now an ordinary unknown-backend error. A non-KDE Wayland desktop now defaults to the **headless nested KWin session** (updated 2026-08-27 per the minimum acceptance bar above; the windowed session is a debugging opt-in only) — an isolated agent desktop with its own cursor, running invisibly with the Computer pane as its screen — and when `kwin_wayland` is missing the failure names the package to install instead of touching the human's seat.
- **Genuine known gaps (only these):** an Xwayland client's own override-redirect menus (unmanaged `X11Window`s the hit test skips; Wayland-native menus including Chromium's are fine); protocol-level drag-and-drop and client-side-titlebar window moves (refused by design — see the drag-and-drop entry); real-desktop control on compositors without a plugin system (GNOME/Mutter, the wlroots family) — those get the headless nested desktop, which is the floor, not the bar. "Chromium/Electron/Xwayland are refused, use the nested session" is **superseded** — that was the pre-direct-injection (pre-V15) model.
- **Out of scope, stated rather than implied:** an **X11 session** (`XDG_SESSION_TYPE=x11`) has no tier — every mechanism here is a Wayland one (a KWin or Hyprland plugin loaded into the compositor, or a nested KWin session), and the probe refuses with "Synara's desktop control is Wayland-only" rather than half-working; Xwayland _clients inside a Wayland session_ are fully in scope and unaffected. **musl systems** (Alpine and kin) get no prebuilt plugin — the prebuild matrix is glibc distributions, so no shipped binary carries a musl distribution's os-release ID, and the lineage fallback refuses outright when the host's glibc cannot be read (`runtimeGlibcVersion()` returns nothing on musl, by design) — so their path is the source build, which works wherever the toolchain and headers exist. Neither is a bug report waiting to be filed; both are boundaries the refusals name honestly.
- **If an agent reports "clicks return true but nothing lands":** it is almost always the agent driving through a hand-rolled script instead of the native `computer_*` tools (which happens when it has no tools), or mis-targeting. Verify with a native `computer_click` before concluding a reach bug. Never answer a reach gap by restarting the app or touching the human's seat.

## What you asked for

A second cursor, independent of yours, that does things on your real desktop while you keep working, with no fighting over the pointer, and you can see the agent's cursor. Just like the macOS version.

We can build this, and Phase 0 has now proven the load-bearing part on the reference machine. A KWin plugin built here loaded into the live compositor, painted its own overlay cursor, and enumerated the real desktop's windows, all without touching the human pointer. The full record is in `docs/computer-use-phase0-results.md`. An earlier draft of this document said the mechanism was impossible on Wayland. That was wrong: it measured Linux at the wrong privilege level. This version reflects what actually built and ran.

## The insight, and where I got it wrong

macOS does not let a normal application move a second cursor. It has one system cursor, same as Wayland. Codex's ghost cursor works because it borrows authority that sits _below_ the shared input pipeline: it hands each event straight to the target application's process, stamped with window-local coordinates, using a private call that only works with WindowServer-level trust. The real pointer never moves because the event never enters the stream that would move it. Then Codex draws a fake cursor picture on top so you can see where it is acting.

My earlier draft compared that to an unprivileged Wayland client and concluded "impossible." True, but irrelevant. An unprivileged client cannot do it on macOS either. The question is not "can a client do it," it is "who has the authority to route an event to one window without touching the seat pointer, and can we run our code there."

On Linux, that authority is the compositor. On this machine the compositor is KWin, and **KWin takes plugins.** A plugin runs inside the compositor process with the same authority KWin has over input routing. That is the exact privilege level Codex operates at on macOS. So the macOS mechanism ports, structurally, one to one.

## The mechanism

Wayland input is just messages on a per-client socket. When KWin wants an app to see a click, it sends `wl_pointer.enter`, `wl_pointer.motion`, `wl_pointer.button`, `wl_pointer.frame` to that client's pointer resource. The app trusts those messages because they came from the compositor. Nothing in the protocol says the compositor may only talk to one client at a time. It normally does, because there is one physical pointer, but that is policy, not a limit.

So a KWin plugin can:

1. Pick a target window (its `SurfaceInterface`, and from that the `wl_client`).
2. Emit a full pointer or keyboard sequence directly to that client's input resources, with coordinates local to that window.
3. Leave the real seat pointer completely alone. Your cursor does not move. No other client sees anything.

Two apps now believe they have pointer focus at once. That is fine. They cannot see each other. This is the line-for-line Linux twin of Codex's per-process event posting.

The visible agent cursor is a KWin scene overlay `Item`, a `ShapeCursorSource` fed into an `ImageItem` at z=1000, parented to `effects->scene()->overlayItem()`. This mirrors KWin's own `CursorItem`, and Phase 0 confirmed it is the right approach. An earlier draft proposed a `zwlr_layer_shell_v1` surface for this; that would work but it is the wrong tool once the code already runs inside the compositor, where drawing straight into the scene is simpler and needs no separate client. Either way it is a non-interactive overlay, the twin of Codex's click-through "Software Cursor" window: your real clicks never hit it because it is not an input target.

**Independence comes from a dedicated agent seat.** The plugin creates a second `SeatInterface` named `synara-agent` on the Wayland display (public KWin API) and delivers all agent input on it. Wayland toolkits handle seats appearing at runtime, so every client picks it up live. The agent seat mirrors the real keyboard's xkb keymap and tracks its own `xkb_state` for modifier events. The user's real seat is never touched in either direction: agent keys cannot land in the user's window, user keys cannot be captured by the agent's target, and both can type at once. An earlier build time-shared the real seat's focus instead, and a live test with the user active showed exactly the crossover that design invites; the dedicated seat closed it.

Side by side:

| macOS (Codex)                                    | Linux (KWin plugin)                                                              |
| ------------------------------------------------ | -------------------------------------------------------------------------------- |
| WindowServer routes input                        | KWin routes input                                                                |
| Private `CGEventSetWindowLocation` + post to PID | server-side `wl_pointer.enter/motion/button/frame` to the target client resource |
| Real pointer untouched, bypasses the HID stream  | real seat pointer untouched, direct per-resource send                            |
| Runs at WindowServer trust via private API       | runs inside the compositor as a plugin                                           |

## Confirmed on this machine

Not speculation. The plugin built, loaded, and ran here on 2026-08-15 (full record in `docs/computer-use-phase0-results.md`).

- Compositor: KWin 6.7.3, Plasma 6.7.3, Wayland session.
- **`kwin-devel-6.7.3` is installed.** Internal KWin headers are present under `/usr/include/kwin/` (`core/`, `cursor.h`, `cursorsource.h`, `compositor.h`, and the rest). The plugin compiles against this exact KWin.
- **Runtime plugin load works.** `busctl --user call org.kde.KWin /Plugins org.kde.KWin.Plugins LoadPlugin s SynaraComputerUsePlugin` returned `true`, and `UnloadPlugin` removes it cleanly. (This is the `/Plugins` binary-plugin interface, distinct from `/Effects loadEffect` and `/Scripting loadScript`.)
- **Scene overlay and window enumeration confirmed live.** `healthJson` reported the overlay, workspace, and effects handles all reachable; `windowsJson` returned real window bounds and PIDs across all three monitors.
- AT-SPI2 running (`org.a11y.Bus`, owned by KWin) for the accessibility tree.
- PipeWire running for capture, and KWin exposes `org.kde.KWin.ScreenShot2`.
- No external fake-input global (`org_kde_kwin_fake_input`, wlroots virtual pointer) is exposed. That confirms the outside-in client paths are closed here, which is precisely why the answer lives inside the compositor.

Everything the primary design needs is already on the machine, and the core of it has run.

## The honest costs

I would rather name these now than have them surface in review.

- **KWin's internal API is not ABI-stable.** A native plugin is built against one KWin version. We pin to 6.7.x and rebuild per KWin release. This is the direct Linux analog of macOS private APIs breaking between releases, and it is the main ongoing tax. Mitigation: keep the plugin small and mechanical, isolate all version-specific calls behind a thin shim, and gate load on a version check with a clear message when KWin moves.
- **It is KDE-specific.** The plugin path works on KWin. GNOME (Mutter) has no comparable out-of-tree plugin interface, and other wlroots compositors differ again. We handle that with the tiered design below, so KWin gets the full macOS-equivalent experience and other environments get a working, lesser mode rather than nothing.
- **Trust.** The plugin runs inside the compositor. That is real privilege. It is the same bargain macOS makes with TCC-granted accessibility, but the user is installing compositor-level code, so the consent and provenance story has to be explicit.

## Three tiers, best available wins

One backend interface, three implementations, chosen at runtime by what the environment supports. This keeps the ambitious path and a graceful fall-off.

**Tier 1, KWin plugin. The macOS-equivalent path. Primary on this machine.**
A dedicated agent seat plus a scene-overlay ghost cursor, on your real desktop, able to drive arbitrary windows including ones you already have open. This is the full "just like macOS" experience. Requires KWin and the matching plugin build.

**Tier 2, Wayland proxy. Portable, agent-launched apps on the real desktop.**
We run a small Wayland proxy and launch the agent's apps with `WAYLAND_DISPLAY` pointing at it. The proxy forwards their buffers to the real compositor, so their windows appear as normal windows on your actual screen, mixed with yours. Because we sit on the far end of those apps' sockets, we inject synthetic input straight into them, exactly as the app expects, without touching your pointer. This is the same philosophy as Codex, intercept at event delivery to the target, and it works on any Wayland compositor, not just KWin. The one gap versus Tier 1: it can only drive apps it launched through the proxy, not windows that were already open under the real compositor. For agent work that is usually fine and safer.

**Tier 3, nested compositor. Isolated sandbox for CI, headless, and unsupported desktops.**
Run a full nested compositor (a wlroots kiosk like `cage`/`sway`, or nested `kwin_wayland`), give the agent its own isolated desktop, capture it over PipeWire into a Synara pane, inject into the seat we own. Fully isolated, needs no special compositor support, runs with no display in CI against the fake backend. This is the safe floor and the test harness, not the headline experience.

Recommended default: Tier 1 where KWin is present, Tier 2 elsewhere, Tier 3 for CI and headless. The backend interface hides the difference from the tool layer.

### Capture

PipeWire is the standard Wayland capture transport and is already running. For Tier 1 and Tier 2 the windows live on the real compositor, so capture the relevant output or window and feed frames into the existing frame transport (`deviceFrameTransport.ts`, `/ws/device-frames`), generalized to also serve the computer pane. For Tier 3 we capture the nested compositor's own output. Encode to the format the device pane already renders so the web side is close to free.

The Phase 2 capture spike (`docs/computer-use-capture-notes.md`) settled the path ordering on KDE. `org.kde.KWin.ScreenShot2` is gated on a desktop-entry authorization and was observed rejecting a normal process with `NoAuthorized` on this machine, so it is not a daemon option. The portal ScreenCast route works but normally costs an interactive consent dialog at `Start`. The primary path is therefore capture inside the Tier 1 plugin itself (offscreen filtered `SceneView` render, the same mechanism KWin's own screenshot plugin uses), with portal ScreenCast as the consent-aware fallback and for Tier 2/3.

### Input

- Tier 1: all agent input rides the dedicated `synara-agent` seat from inside the plugin, driven through the plugin's D-Bus interface `org.synara.ComputerUse1` (`movePointer`, `button`, `axis`, `key`, `focusWindow`, `clearFocusWindow`, plus `healthJson` / `stateJson` / `windowsJson` for introspection and `start` / `stop` for the session). Keys go through `SeatInterface::notifyKeyboardKey` on the agent seat with plugin-tracked xkb modifier state; the real keyboard pipeline is never involved. Pressed buttons and keys are tracked and released on stop or plugin destruction, so a mid-action stop cannot latch a stuck modifier. This is the whole point of the tier.
- Tier 2: synthetic events written into the proxied client streams.
- Tier 3: virtual pointer/keyboard into the seat we own (wlroots virtual-input protocols on `cage`/`sway`, or `libei` against nested `kwin_wayland`).

`libei`, `libeis`, `libinput` are all installed, and `/dev/uinput` exists, so the lower-level fallbacks are available if a tier needs them. `ydotool` at the kernel level stays a last resort only, because it injects globally and would move the real pointer, which defeats the entire goal.

### Perception

AT-SPI2 first for structure (roles, names, positions), the Linux analog of the macOS AX tree, with `org.a11y.Bus` already live. Pixels second, from the capture stream, for anything AT-SPI does not expose. Targeting reuses the device family's snapshot-then-act idiom: act on a named element, prefer an element's own point over a frame center, and surface candidate labels in the error when a target is ambiguous.

### Capability model

`AgentGatewayCapability` in `apps/server/src/agentGateway/Services/AgentGatewaySessionRegistry.ts:4` currently spans `thread:read`, `thread:write`, `automation:write`, `diagnostics:read`, `browser:control`, `device:control`. Add `computer:control`.

It must not join the blanket default in `PROVIDER_SESSION_CAPABILITIES` (`Layers/AgentGatewaySessionRegistry.ts:12`), which grants every listed capability to every provider session. Driving the real desktop through a compositor plugin is the most consequential thing Synara could do, so `computer:control` is opt-in per provider, and the action tools are approval-required.

### Tool surface

Perception, read-only, no approval, still behind `computer:control`:

- `computer_list_windows`, `computer_get_state { include_screenshot?, include_text? }`, `computer_screenshot { window_id? | x?, y?, width?, height?, max_dimension? }`, `computer_get_screen_size`, `computer_launch_app`.

`computer_get_state` returns one downscaled shot of the whole multi-monitor workspace, which is too coarse to read small text. `computer_screenshot` is the zoom: one window or one desktop rect captured against the same `max_dimension` budget. Every screenshot the tools deliver — workspace, zoom, or post-action observation — gets a `screenshotId`, and the pointer tools take `x`/`y` as pixels in the most recent one (or the one named by `screenshot_id`), measured from its top-left corner; a per-thread frame registry on the server (`screenshotFrames.ts`) turns those pixels into desktop points, so the model never does `region + pixel / scale` arithmetic itself. This is the same contract the Codex app's computer-use client and Anthropic's computer tool use, and it replaced the earlier design where the model was handed `region` + `scale` and asked to convert: a model that had to compute the mapping across an offset, downscaled capture mis-aimed often enough to be the dominant failure in live runs. The `region` and `scale` still travel with each image for the pane and for debugging. Scroll distances and `computer_screenshot` rects are read in the same screenshot pixels; a point outside the image is refused rather than landing on whatever the desktop shows beside the window, and a pointer call before any screenshot is refused with a nudge to look first.

Action, approval-required:

- `computer_click`, `computer_double_click`, `computer_right_click`, `computer_move_cursor`, `computer_drag`, `computer_scroll`.
- `computer_type_text`, `computer_press_key`, `computer_hotkey`.
- `computer_set_value`, `computer_perform_action` for AT-SPI semantic writes.
- `computer_write_clipboard`, which replaces what the human last copied.
- `computer_read_clipboard` — the one read that requires approval. It mutates nothing, but the clipboard can hold something the human copied privately (a password manager entry, a token) that is not otherwise visible to the agent, so it must never be auto-approved the way perception tools are; its MCP annotations deliberately do not claim `readOnlyHint`. Reads are also bounded by the 16 KiB contract limit on `value`; writes accept up to 1 MiB and do not echo the text back.

Same refuse-rather-than-guess rule as the device family. If a target is ambiguous or off-screen, return a structured error with candidates instead of clicking the wrong thing.

### Shared extractions

Per the repo's maintainability rule, this should cut duplication, not add it.

1. Stdio JSON-RPC transport. There are already two copies (Codex app-server in `codexAppServerManager.ts`, device helper in `helperClient.ts`). Extract framing, correlation, timeout, and respawn into `packages/shared` (subpath export, `@synara/shared/jsonrpc-stdio`) and move both onto it. Tier 1 talks to the plugin over D-Bus, not stdio, but Tiers 2 and 3 need this transport, so they reuse the shared copy rather than adding a third.
2. Frame transport. Generalize `deviceFrameTransport.ts` and `deviceFrameRoute.ts` into a shared `FrameTransport` so `/ws/computer-frames` reuses it. `packages/shared/src/deviceFrame.ts` already holds the header logic.
3. Targeting. `uiTreeTargeting.ts`'s snapshot-then-act idioms generalize to an AT-SPI targeter.
4. Contracts in `packages/contracts` (schema only): `ThreadComputerState`, `ComputerAvailability`, `ComputerEvent`, the frame header, and a `WsComputerRpcGroup` in `rpc.ts`, mirroring `device.ts`.
5. Any expand/collapse in `ComputerPanel` reuses `apps/web/src/lib/disclosureMotion.ts`. No bespoke toggle animation.

## Consent and safety

- `computer:control` is opt-in, never a default provider capability.
- Action tools are approval-required via `COMPUTER_APPROVAL_REQUIRED_TOOLS`. Perception is read-only.
- The plugin ships as identifiable, versioned code, loaded explicitly over `org.kde.KWin/Plugins` with the user's consent, and reports which KWin version it was built for (a mismatched build is refused by KWin, as Phase 0 confirmed). Installing compositor-level code is a deliberate act, presented as one.
- A visible session indicator shows which thread is driving and offers an immediate stop. Since Tier 1 acts on your real desktop, **Meta+Shift+Esc** releases control from any window (Phase 3b), and the ghost cursor is the on-screen marker whenever the agent is live.
- The session has a plugin-side deadline (5 minutes idle by default). The kill switch and the deadline both live inside the compositor, so neither depends on a server that may have crashed.
- The agent cannot drive KWin's own security or authentication prompts, matching the macOS limitation, so it cannot approve its own escalations.

## Known limitations

### Drag-and-drop and titlebar moves are refused, by design

Read off the KWin 6.7.3 source 2026-08-19. **The agent cannot start a Wayland drag-and-drop, and cannot drag a window by its client-side titlebar.** This is not a gap waiting to be closed; the mechanisms that would close it all take the human's seat, and the whole feature is that it does not.

Both gestures are client requests, not input events. A client starts a drag with `wl_data_device.start_drag` and asks to be moved with `xdg_toplevel.move`, and both carry the serial of the button press that began the gesture. KWin validates that serial against a real implicit grab: `SeatInterface::hasImplicitPointerGrab` looks it up in the seat's button-serial table and requires that button to still be down (`src/wayland/seat.cpp`). Neither agent path can produce such a serial.

- **Direct injection** (Chromium, Electron, everything behind Xwayland) mints serials from the display counter and writes to the client's own `wl_pointer` resources, so seat0 never saw the press and its grab table has never heard of the serial. `DragAndDropInputFilter` falls through the pointer, touch, and tablet branches and calls `source->dndCancelled()` (`src/input.cpp`): the drag ends before it begins, and the client is told only that its own drag was cancelled. `XdgToplevelWindow::handleMoveRequested` gets `std::nullopt` from `implicitGrabPositionBySerial` and drops the request without a word (`src/xdgshellwindow.cpp`).
- **The agent seat** holds a genuine implicit grab of its own, and it is still no good. KWin builds one `DragAndDropInputFilter`, wired to `waylandServer()->seat()`, so a drag begun on the `synara-agent` seat reaches no listener at all — not even the cancel. A titlebar move would be worse than useless: the serial check passes, and then the anchor comes from `input()->globalPointer()`, which is the human's cursor, so the window would follow the human's pointer rather than the agent's.

The workarounds were considered and refused as a set, because every one of them ends the same way. Minting a grabbing serial means calling `notifyPointerButton` on seat0, which moves the human's pointer focus and drives their cursor. Handing the agent seat to KWin's drag filter means making the agent seat the compositor's seat. Reimplementing DnD above the protocol means moving the real cursor to paint the drag icon. The dedicated seat and the ghost cursor are the feature — the agent works while the human works — and a drag that briefly commandeers the human's pointer is a worse product than a drag that does not exist.

What still works, and what to do instead:

- Press-move-release pointer drags are unaffected on both paths and are what `computer_drag` does: text selection, sliders, canvas strokes, resize handles inside a client. Only the protocol-level DnD handshake is out.
- Between windows, use the keyboard-driven equivalent the application already has — cut/copy and paste, a "Move to…" menu item, a file dialog — which the agent reaches through the input paths that do work.
- Windows are moved by the compositor, not the client: the agent asks KWin instead of dragging the titlebar.

### Xwayland's own menus are still out of reach

Read off the source, not yet measured live. Pointer targeting accepts popup windows (see the popup entry in Phase 4), but an X11 client's menus are override-redirect windows, which KWin models as unmanaged `X11Window`s, and every targeting predicate in the plugin starts at `isClient()`, which those answer `false`. So a menu opened by an Xwayland application is skipped by the hit test and a click aimed at it lands on whatever it is drawn over. Wayland-native menus — including Chromium's and Electron's, which are `xdg_popup`s — are unaffected.

_Phase 3b, session lifetime and the kill switch. Idle timeout + release hotkey landed 2026-08-16 (plugin compiles against KWin 6.7.3; not yet loaded into a live compositor)._

Both safeguards live in the plugin, because the failure mode they exist for is a server that is no longer running. Killing the server mid-stream used to leave the agent seat and the ghost cursor alive indefinitely, since Effect finalizers don't run on a hard kill.

- **Idle timeout.** A running session stops itself after 5 minutes without agent activity, taking the full `stop()` path (pressed buttons and keys released, focus dropped, cursor hidden, in-flight capture canceled). Input, focus, and capture calls reset the deadline; `healthJson`/`stateJson`/`windowsJson` deliberately do not, or the server's own health poll would keep every session alive forever. `setIdleTimeout(u milliseconds)` reconfigures it (`0` disables; otherwise 1 s – 1 h), and `KWinComputerBackend` sends its configured value right after each `start()`, tolerating an older plugin that has no such method. `stateJson` exposes `idleTimeoutMs`, `idleMs`, `idleRemainingMs`, and the last `stopReason`.
- **Release hotkey.** `Meta+Shift+Esc`, registered from the plugin through KGlobalAccel (`SynaraReleaseComputerControl`, remappable in System Settings), free on stock Plasma. It works regardless of focus, and because agent input goes straight to client surfaces on the `synara-agent` seat without entering KWin's input pipeline, the agent can neither trigger it nor swallow it. It stops the session and latches: `start()` then fails with `org.synara.ComputerUse.Error.ControlReleased`. Pressing it again hands control back (an explicit D-Bus `stop()` also clears the latch, but the server only calls that at shutdown — on a running server the hotkey is the user's toggle).
- **Input is gated on the session.** Every input method now returns `false` while stopped. Before this, an auto-stopped plugin would still have injected input with the ghost cursor hidden.
- **Server-side recovery is deliberate, and asymmetric on purpose.** The server learns about an external stop from that `false` (plus a `healthJson` read), not from a subscription: a `sessionStopped(s reason)` signal is emitted for `busctl --user monitor` diagnosis, but nothing consumes it yet, and polling-on-rejection costs nothing on the happy path. An **idle** stop is restarted transparently and the call retried once, because a model that thinks for six minutes between clicks will routinely trip the deadline and that must not fail the turn. A **hotkey** stop raises a clear, non-retryable error naming the hotkey and how to hand control back — silently restarting the session on the agent's next action would defeat the panic switch.
- **Known interaction.** While the web `ComputerPanel` is open, its 500 ms still-frame poll counts as capture activity and holds the deadline open. That is the specified behavior (capture is agent activity), and it only applies while a human is watching the stream; the server-side fix, if we want one, is to stop polling when nothing is happening.

**Phase 4, portability and hardening.**
Tier 2 (Wayland proxy) for non-KWin compositors and Tier 3 (nested compositor) for CI and headless, behind the same backend interface. Multi-session, health metrics, crash recovery, clipboard handling, and the KWin-version gate with a clean upgrade message.

Landed so far: occlusion-aware click targeting (z-order + `occludedBy` in the window list, plugin `raiseWindow`, raise-before-interact, version-skew tolerance for older live plugins); the KWin-version gate (the installer stamps the KWin version it built against, and a load refusal names both versions and the fix) plus a `SYNARA_COMPUTER_IDLE_TIMEOUT_MS` override; the hotkey-reliability fix below; clipboard tools on the wl-clipboard fallback; KWin crash recovery; multi-session arbitration; live health metrics; the Tier 1 human-active guard; and the Tier 3 nested-compositor backend.

Health metrics. Availability used to be a boot-time snapshot frozen into the service layer, so a crashed compositor kept reading as "available" while the backend quietly reconnected. The backend now exposes a synchronous health snapshot (connected / reconnecting / unavailable, consecutive failures, reconnects since startup, last failure, capture availability) derived entirely from supervision state the connect and reconnect paths already maintain — reading it never costs a D-Bus round trip. Transitions ride the existing backend event subscription; the manager republishes thread state from cache only, so a failure event cannot trigger another connect attempt. Thread availability degrades honestly while reconnecting (which also disables the composer's computer-control toggle for the duration), and the panel header shows a reconnecting/unavailable indicator that outranks the lease and agent badges.

KWin crash recovery. A compositor crash does not drop the backend's session-bus connection — only KWin's bus names vanish — so calls to the stale proxy fail with `ServiceUnknown`/`NameHasNoOwner` rather than a disconnect. Those were classified as method-level errors: no proxy invalidation, no reconnect, and a stale healthy flag short-circuited every later ensure, leaving computer use dead until a server restart. Both error types are now connection-level, so the existing supervision path (invalidate, backoff reconnect, re-load the plugin into the restarted compositor) covers a crashed-and-restarted KWin. A regression test walks healthy → crash → restart-without-plugin → recovered listing.

Multi-session arbitration. Every conversation shares one `ComputerManager`, but there is one desktop, one cursor, and one keyboard focus. The first thread to perform a mutating action now implicitly holds an exclusive desktop lease; other threads' mutating tools get a structured retryable refusal (`computer_controlled_by_other_thread`) while perception stays free, so a blocked thread can watch and retry. Release is driven by the provider runtime stream (`turn.completed` / `turn.aborted` / `session.exited` — the orchestration domain vocabulary has no turn-end event), with a 300 s idle expiry as the crash backstop that never fires while a call is in flight. Clipboard access is leased like input (one shared slot), pane input from the human neither takes nor is blocked by the lease, and `ThreadComputerState.controlledByOtherThread` surfaces the blocked state as a badge in the computer pane.

Hotkey reliability (investigated live 2026-08-16, WAYLAND_DEBUG-traced). Two distinct bugs made agent-sent keyboard shortcuts unreliable:

1. **Activation gates shortcut dispatch.** Toolkits derive "is my window active" from xdg_toplevel's `activated` state, which KWin drives from the human's seat; `wl_keyboard.enter` on the agent seat doesn't affect it. Qt's shortcut matcher refuses to match QAction shortcuts with no active window, while plain key events still reach the focus widget and pointer clicks never consult activation. Signature: typing works, Shift composes capitals, clicks fire actions, Ctrl-chords silently vanish. Per-app tolerance varies (KWrite strict, KCalc/Konsole lenient — the early E2E's Ctrl+Q worked because freshly launched windows are activated). Fix: while the agent's keyboard focus rests on a window the human hasn't activated, the plugin borrows activation via `Window::setActive(true)` (visual/state only; the human's focus never moves), undone when focus moves on and never undone if KWin has since granted activation for real.
2. **Dead targets misdirected chords.** When the named keyboard target died, the plugin silently fell back to the window under the pointer, and `setFocusedKeyboardSurface(surface, pressedKeys)` handed the next client a phantom held Ctrl via the enter pressed-key array — a Ctrl+Q aimed at a closing window executed in an unrelated app. Fix: a dead target is now an error, not a fallback (key methods return `false`; `stateJson` reports `targetLost`), and held keys never migrate across a focus change (released to the old surface first, or dropped with the xkb state rewound when the surface is gone).

The window list now exposes `active` per window and `stateJson` reports `keyboardWindowActive` / `borrowedActivation` / `targetLost`, so both the server and a diagnosing human can see the difference between "keys delivered" and "shortcuts will dispatch".

Four of five items passed outright: borrowed activation shows in `stateJson`; a dying target flips `targetLost` and key calls return `false` instead of retargeting; no phantom modifiers survive a focus migration (held Ctrl on window A, focus moved to B — B's `wl_keyboard.enter` carried an empty pressed-key array and `modifiers(0,0,0,0)`, `pressedKeyCount` dropped to 0); and the human's focus never visibly moved. The chord item was partial: KWrite accepts Ctrl-chords from the agent seat whenever the borrow arrives with a fresh `wl_keyboard.enter`, but a precise sequence killed them — activate the borrowed window for real, then activate another window (KWin revokes the borrowed window's active flag), then re-focus the same window from the agent. The plugin's borrow pointer still matched, so `updateWindowActivation` returned early without re-applying `setActive(true)`: `stateJson` showed `borrowedActivation: true` with `keyboardWindowActive: false`, text still typed, and every chord died. A second, cosmetic finding from the same run: a borrowed window keeps `active: true` in the window list alongside a window the human has since genuinely activated, so two windows can report active at once; that is inherent to the borrow design (the agent's chords must keep working when the human switches away) and is left as-is.

The fix is plugin-side, lazy, and two-part — the V5 live run proved one part is not enough. Part one: `updateWindowActivation` no longer trusts the borrow pointer alone; when the borrowed window has lost its active flag it re-asserts `setActive(true)` on the next focus or key call, rather than from a signal handler that would fight the compositor mid-activation. V5 verified the state machine (`keyboardWindowActive` flipped back to true on a bare key call, the window list showed `active` again) but the chord still died: re-sending xdg `activated` alone leaves Qt's shortcut matcher dead. The reason is the human's seat itself — the revocation only happens because real activation churned through the window, and the `wl_keyboard.leave` that seat0 sent on the way out reset the client's keyboard-focus state, which no event on the agent seat had since refreshed. Verified live by isolation: from the dead state, a `clearFocusWindow` → `focusWindow` cycle (fresh agent-seat enter, activation state unchanged) revived the chord instantly. Part two therefore makes the same-window path in `updateKeyboardFocus` cycle the agent seat's focused keyboard surface (leave then enter, carrying any held keys) whenever the keyboard window has lost its active flag, before the activation re-assert. Since `key()` re-runs that path before every event, this heals bare hotkeys sent after the human switches windows, with no focus call in between, at the cost of one extra leave/enter per revocation event. A server-side workaround was rejected: `clearFocusWindow` re-derives keyboard focus from the pointer, so the cycle is a no-op exactly when the ghost cursor still hovers the target window, which is the common case. Both parts went live as V6 and the kill sequence was re-run 2026-08-17: from the revoked-borrow state (`borrowedActivation: true`, `keyboardWindowActive: false`), a bare Ctrl+N with no focus call re-asserted the borrow and dispatched — KWrite opened a new tab. Every item on the live checklist now passes.

Clipboard (implemented on the fallback mechanism). Qt apps use seat0's data device regardless of which seat delivered input, so the agent seat cannot have a private working clipboard: an agent-driven Ctrl+C takes the human's. This entry used to claim that such a copy fails serial validation and is silently cancelled. It does not, and the correction matters because the real behavior is the more dangerous one. `SeatInterfacePrivate::updateSelection` compares the request's serial against the last selection's and nothing else (`src/wayland/seat.cpp`) — there is no grab check, no focus check, nothing tying the serial to an event the client actually received. Serials on both agent paths come from the display's own counter, so they are never stale, and the copy succeeds: the application puts its selection on seat0's clipboard, KWin accepts it, and whatever the human had copied is gone. The human's next paste is the agent's data, with no indication of where it came from. Therefore `computer_read_clipboard` / `computer_write_clipboard` must target seat0's clipboard explicitly and document it as shared with the human, and must never be implemented by synthesizing Ctrl+C/V — not because the synthesis would fail, but because it works and destroys something of the human's while looking like an ordinary tool call. Preferred mechanism: in-plugin `SeatInterface::setSelection()` on `waylandServer()->seat()` (bypasses serial validation, Klipper-visible); acceptable fallback: external `wl-copy`/`wl-paste` on the default seat. One packaging wrinkle: Fedora's kwin-devel omits `abstract_data_source.h`, which may constrain the in-plugin data-source subclass.

Shipped on the fallback: `apps/server/src/computer/wlClipboard.ts` runs `wl-paste --no-newline --type text` and `wl-copy --type text/plain` with no `--seat` flag, which lands on seat0 because it exists before the plugin creates the agent seat. Both types are explicit for a reason: without one, wl-paste streams an image's raw bytes back as "text", and wl-copy labels an empty write `application/x-zerosize`, which then reads back as non-text. An empty clipboard exits non-zero with "Nothing is copied" and is mapped to `""`. The in-plugin `setSelection()` route stays the eventual refinement; it would replace the runner behind the same `ComputerBackend.readClipboard` / `writeClipboard` methods.

Seat reach, and what the nested session is actually for (measured live 2026-08-19, WAYLAND_DEBUG-traced). The dedicated seat has one hard limit, and it is not a bug in the plugin: Wayland delivers input per resource, so a client that never bound the `synara-agent` seat has nowhere for its events to go and they are dropped with no error at any layer — the agent believes it clicked. Which toolkits bind a seat added at runtime was measured rather than assumed. Qt binds it. Gecko binds it. **Chromium/Ozone does not** — it binds exactly one `wl_seat`, the first the compositor advertises, and ignores every later global; so does **Xwayland**, on behalf of every X11 client behind it. GTK does bind it, which is why an Electron app's GTK connection appears to work while the Ozone connection that owns the window does not. Neither Chromium nor Xwayland can be talked out of this, and seat0 always wins the race because the compositor creates it before any plugin loads.

Two changes follow, and together they are the whole answer.

First, **the plugin refuses instead of pretending**. `clientBoundAgentSeat()` walks the target client's resources (`SurfaceInterface::client()` → `ClientConnection::client()` → `wl_client_for_each_resource`, matching `SeatInterface::get()`) and asks whether that client holds the agent seat at all. If not, `focusWindow`, `button`, `axis`, and `key` fail with `org.synara.ComputerUse.Error.SeatUnsupported`, naming the application and the remedy; `KWinComputerBackend` passes that text through as a non-retryable error rather than the generic "aim elsewhere in the window" advice a refused injection carries. `movePointer` is deliberately exempt — gliding the ghost cursor over an unreachable window is harmless, and the refusal belongs on the action. It looks for `wl_seat` and not `wl_pointer` because a client that bound the seat but has not yet asked it for a pointer is still reachable; one that never bound the seat cannot become reachable.

Second, **a compositor the agent owns is driven through its own input stack, not a second seat**. `SYNARA_COMPUTER_USE_OWNS_COMPOSITOR=1`, set only by `nestedKWinSession.ts` when it spawns the nested compositor, makes the plugin add a `SynaraVirtualInputDevice` (a `KWin::InputDevice`) to `input()` instead of creating a seat. Events then enter KWin's normal pipeline: focus follows clicks, real activation replaces the borrowed-`activated` workaround entirely, KWin owns the xkb state so there is nothing to mirror, KWin draws the cursor so there is no ghost cursor and none is wanted, and Xwayland forwards to X11 clients. There is no human in that compositor to protect, which is the only reason this is allowed — and it is an environment variable rather than a D-Bus method precisely so nothing reachable over the bus can talk the plugin into driving the human's seat. The nested session also now starts `--xwayland` and reports the display KWin picked for it via `xDisplay` in `healthJson` (only the in-process plugin can know it: KWin publishes it by `setenv` on itself, with nothing on the bus and nothing parseable in its output), which `nestedSessionEnv` passes to launched clients as `DISPLAY` — always set, empty when unknown, so an X11 client with nowhere to go fails instead of opening on the human's screen.

Verified live in a nested session (plugin V13): an Electron/Chromium window took a click at the exact point (the page reported `CLICKED 400,257`), took typed text, and **acted on Ctrl+A — the selection highlighted** — and an X11 `xmessage` exited 0 when the agent clicked its Yes button. The same click against the same Electron app on the human's desktop refuses with the named error. The host session is unchanged: `dedicatedSeat: true`, `ownsCompositor: false`, ghost cursor intact.

**Direct per-client injection closed the gap on the human's own desktop (2026-08-19, plugin V15).** The refusal above was honest but it was not parity: on macOS an agent reaches every application, and routing Chromium and X11 to a nested session the human cannot see is a different feature. The fix is the literal Wayland twin of what Codex does on macOS with `CGEventSetWindowLocation` plus a post-to-PID: stop trying to make the client listen to a seat it never bound, and write to the input resources it _did_ bind. `clientInputResources()` enumerates the target client's `wl_pointer`/`wl_keyboard` resources, and the plugin calls `wl_pointer_send_enter/motion/button/axis/frame` and `wl_keyboard_send_enter/key/modifiers/leave` on them directly, bypassing `SeatInterface` entirely. Going _through_ the seat is what would move the human's focus; talking to the client does not, and KWin never learns it happened. The client already holds seat0's keymap, so none is sent; modifiers are serialized from the plugin's own xkb state.

The safety property is an explicit invariant, not a hope: a `leave` is never sent to a surface the human's seat has focused (`SeatInterface::focusedPointerSurface()` / `focusedKeyboardSurface()`), so the agent cannot take focus from the person at the keyboard, and the surfaces holding an agent enter are tracked in the plugin because nothing in KWin knows those events exist. `stateJson` now reports `humanPosition` alongside the agent's for exactly this reason — the two cursors moving independently is the whole design, and this is how that gets checked rather than argued about. Verified live on the host session: the human's pointer stayed at 1384.29,1831.09 while the agent moved to 1276,1759, clicked into Electron (`CLICK 396,338`), typed, held Ctrl and pressed A (the page reported `KEYDOWN Control +ctrl`, `KEYDOWN a +ctrl`, and the selection highlighted), and moved on to 3000,600; an X11 `xmessage` exited when the agent clicked its Yes button.

**The seat-vs-injection choice is by pointer-object location, not seat binding (fixed 2026-08-20, plugin V18).** A live probe found a class of clients the reach story missed: a native `computer_click` into a flatpak Zen window returned success and never landed. The plugin `button` reported `true` — so it was not a refusal — yet the page never saw the click, while a Qt KWrite took input fine. Root cause: the path was chosen by `clientBoundAgentSeat` (did the client bind the agent seat's `wl_seat` global), but binding the global and creating a `wl_pointer` _on_ it are two separate Wayland requests. Gecko binds every seat advertised to it and calls `get_pointer` only on the one it treats as primary (seat0), so it bound the agent seat with no pointer object there; `SeatInterface::notifyPointerButton` on the agent seat then had no resource for that client and dropped the event with no error — the exact "returns true, nothing lands" the field reports. The nuance had been mis-recorded as "Gecko binds the seat" (true of the global, false of the pointer object). The fix routes on `PointerInterface::get(resource)->seat() == m_seat` — the pointer object's own seat is authoritative — so the agent seat is used only when it can actually deliver, and everything else (Gecko included, now identical to Chromium) goes through direct injection to its own resources. Because a misclassification can only ever push a client onto direct injection, which is the universal path, the change cannot cost reach and cannot regress the seat clients. Verified live (V18): a backend click into a flatpak Zen window that predates the seat landed at the exact page coordinates, typing landed, and a Ctrl+W chord closed the window, while KWrite kept working through the unchanged seat path and the human pointer stayed put.

So the tier boundary is now the ordinary one. Tier 1 on the human's desktop reaches every application — Qt, GTK, Gecko through the dedicated seat, Chromium/Electron and everything behind Xwayland through direct injection — and keeps the property that makes it worth having: the agent works while the human works, on its own cursor. `requireReachableClient()` refuses only a client that holds no pointer or keyboard on _any_ seat, which is a client with nothing to inject into. The nested session is no longer the fallback for browsers; it is what it always should have been, an isolated desktop for when you want one. One known caveat: injecting into Xwayland moves the X-level pointer position, so an X11 client that _queries_ the pointer sees the agent's coordinates. The human's visible KWin cursor is unaffected, and no Wayland client is affected.

**Menus were untargetable, on both delivery paths (fixed 2026-08-19).** Every targeting predicate in the plugin ended at `Window::wantsInput()`, and KWin's `XdgPopupWindow::wantsInput()` returns `false` unconditionally — a menu does not want to be activated; it borrows the keyboard through the compositor's popup grab instead. So a context menu, a dropdown, or a combo popup was skipped by the hit test and refused by the explicit-target check, on the agent seat and on direct injection alike: the click went through the open menu into the window behind it, which is exactly the failure that reads as "the click did nothing". The human's compositor delivers those clicks, so this was our filter, not Wayland. The pointer now has its own predicate, `pointerUsableWindow`, which accepts a window that either wants input or answers `isPopupWindow()` — true for every `xdg_popup` by construction, plus the window-type popups that managed X11 and internal windows declare. Nothing else widens: the window still has to be a mapped client on the current desktop, and `hitTest` still honours the surface's input region, so a tooltip that takes no input is still not hit. The explicit-target path gained the matching rule, because a menu is a window of its own: a click is accepted when it lands on the target **or** on a popup in the target's transient tree, deepest first, since a submenu is transient for the menu that opened it and drawn above it. Walking down from the target rather than up from the stacking order keeps this off the motion path's budget — for a target with no transients it is one empty list. Keyboard policy is deliberately unchanged: `wantsInput()` remains the keyboard's gate, nothing focuses or activates a popup, and menu key navigation keeps working the way it already did, through KWin's own popup filter holding seat0's keyboard for the duration of the grab.

**Getting the plugin onto a machine that has never had it** (`apps/server/src/computer/kwinPluginProvisioning.ts`). Parity is not just reach; it is that a user installs the update, turns computer use on, and it works. Two things stood in the way. The first was `sudo`: a KWin plugin does not have to live in `/usr` — KWin finds plugins through Qt's library paths, and Qt reads `QT_PLUGIN_PATH`. Proven live by booting a KWin with `QT_PLUGIN_PATH` pointed at a temp directory and watching the plugin there appear in `AvailablePlugins` and return `b true` from `LoadPlugin`. So the plugin goes under `~/.local/lib64/qt6/plugins` (the lib64/lib split read off the system Qt rather than guessed, because it is a distro packaging choice), and one small script in `$XDG_CONFIG_HOME/plasma-workspace/env/` puts that root on the path. Nothing outside the home directory is touched and uninstalling is deleting two paths. The second was the compiler: prebuilt binaries per KWin version and architecture ship with the app (`.github/workflows/kwin-plugin-prebuilds.yml` builds them in distribution containers and writes a checksummed `manifest.json`), matched **exactly** on version — never nearest, because a near miss fails at load with no reason given, which turns a clean "no prebuilt, building from source" into an unexplained failure. Building against the local headers stays as the fallback, and `install-and-load.sh --build-only` is that build, so there is exactly one of it. The backend provisions at connect time, at most once, and if KWin refuses a shipped binary it retries with a source build — a prebuilt can be right for the KWin version and still wrong for the distribution's Qt or libstdc++, and that failure is wordless in exactly the same way. The one cost that cannot be engineered away: Qt reads `QT_PLUGIN_PATH` when KWin starts, so the very first install lands somewhere the running compositor was never told about. `sessionSeesPluginRoot()` detects precisely that (the server inherits the session environment, so its `QT_PLUGIN_PATH` is KWin's) and the availability card says to log out once. Every later update loads live.

**A post-action observation never photographs a different window (2026-08-20).** This closes the first defect run six filed. The rule has two halves. A hinted observation — the action named its window — captures exactly that window; when the capture fails because the window is gone, the result is `targetWindowClosed`, and when it fails while the window is somehow still listed, the result is no screenshot at all. Neither branch substitutes another window, because on a live desktop the window holding focus once the agent's target has died is the human's. The untargeted half observes the window under the action's own coordinates first — the compositor routes an unscoped pointer action to the topmost window at its point, so that window is the one the action touched, and photographing it reports the action's outcome rather than anyone's focus (added 2026-08-22, after the Codex OSS form runs: an untargeted scroll cleared the agent's focus target, every scroll observation widened to a workspace downscale too small to read, and the agent scroll-hunted blind). When the point identifies no window — bare desktop, or an overlap the stacking order cannot rank — it observes the agent seat's focus target, widening to the whole workspace when the agent has none; never the compositor-active window as a fallback, which is the human's by definition. The explicit `computer_screenshot` perception path keeps its wider fallback deliberately: an agent that asks to see the focused window may be shown it, and an explicit region capture reaches the same pixels anyway; the defect was an automatic post-action capture drifting there uninvited. Both halves are pinned by tests, including the widening case with the human's browser active and topmost. The review pass later caught the same leak reintroduced through Tier 2 — the GNOME extension reported the human's keyboard focus as `focused`, which the agent-focus-only guard would have read as the agent's target — and forced that provider to `active`-only on both sides.

**A scroll of N pixels travels N pixels in every toolkit (2026-08-22).** The Codex OSS form runs exposed it: the agent's +700 px scroll landed on the page footer thousands of pixels down, and it oscillated (+700, −450, +500…) without ever converging on the form. The stack spoke pixels end to end but injected wheel-source events carrying a value120 half (15 px per notch); Qt clients honor the pixel half exactly — which is why the KWrite E2E measured perfect fidelity — but browsers act on the notch count alone and multiply it by their own per-notch line distance, a ~7× gearing in Gecko. V22 tried finger-source continuous deltas on the theory that every toolkit precision-scrolls those at face value, and controlled measurement (plugin driven directly over live windows, before/after captures correlated) proved the theory wrong twice: Gecko ignored agent-seat finger axis events entirely — a single 300 px burst and a touchpad-cadence 6×50 px stream both moved a form page zero pixels — and KWrite geared them ~5×. V23 therefore reverted to wheel source with the value120 half: it is the one scroll every toolkit acts on, and what varies per toolkit is only the distance, which no compositor-side unit choice can fix — a −250 px wheel scroll moved Zen at least 1900 px while KWrite moved exactly right. So scroll is now closed-loop instead of open-loop: the agent path captures the affected window before and after, correlates the two to get the real travel, returns it as `scroll.traveledY`, and learns a per-window gearing that pre-divides every later request to that window (`apps/server/src/computer/scrollCalibration.ts`). The human's pane scrolls are exempt by construction — they are watching the result and closing the loop themselves, and a correction applied under their hand would fight them. The first live run added the last piece: a full-size first scroll into a 7× browser travels so far that the before/after captures share no content, the correlation refuses, and nothing is learned — the run scrolled to the page bottom and then clicked coordinates from a layout that no longer existed. The first large vertical scroll into an unmeasured window is therefore split: a 48 px probe goes out first (small enough to stay measurable at any believable gearing), its travel is learned, and the remainder — the request minus what the probe already covered — is delivered pre-divided, so even the very first scroll lands near the requested distance. Verified end to end on 2026-08-22: with V23 wheel delivery plus the probe, the Codex OSS form run's two scrolls measured `requested 700 → traveled 704` and `requested 600 → traveled 599` in a Zen window whose learned gearing was 11.3, and a Google Cloud Console IAM run (create service account with role, verify, delete) completed unattended. The correlator additionally refuses winners that are not near-exact matches in absolute terms — a footer's evenly spaced link columns aliased an out-of-range shift into a confident wrong-direction answer once — and a measured travel opposing the injection is suppressed rather than reported. One known residue from the Cloud Console run: Gecko occasionally swallows a pointer click on a just-opened in-page modal button (two dead-center clicks on a confirm dialog's Delete ignored; keyboard Tab+Enter landed), which `screenshotUnchanged` surfaces honestly and the model routes around.

**The human's own window is off the table while they are in it (2026-08-20).** This closes the second defect run six filed. The rule is one sentence: a pointer button, a scroll, or a key whose resolved target is the window seat0 currently has keyboard focus on, while seat0 has seen input inside the last two seconds, comes back as `org.synara.ComputerUse.Error.HumanActive` and nothing is written. Everything else on the desktop proceeds exactly as before — this takes one window away, not the feature.

Where the recency comes from decided how much of this can be trusted. The obvious source is `waylandServer()->seat()->timestamp()`, and it is the wrong one twice over: it is whatever was last handed to `setTimestamp`, which is a value written by anything forwarding events through seat0 rather than a statement about a device, and it carries libinput's clock, which we would then have to assume matches the clock we read it against. The plugin installs a `KWin::InputEventSpy` instead and stamps arrivals with its own `QElapsedTimer`. A spy is called from `InputRedirection` ahead of every filter, which is precisely the set of events neither agent path can produce: the dedicated seat is a second `SeatInterface` that KWin's input pipeline knows nothing about, and direct per-client injection writes to `wl_pointer`/`wl_keyboard` resources without a seat at all. KWin tracks its own user activity the same way (`InputRedirection::m_userActivitySpy`), which is a good sign it is the intended tool.

That is also why **Tier 1 needs no attribution epsilon**, where the Tier 2 arbiter's whole job is attribution. On a portal backend the agent drives seat0 itself, so the arbiter has to subtract its own footprints from what it observes and lives with an ambiguity window while it does. Here the agent's events never enter seat0 by construction, so anything the spy saw is the human, full stop, and the guard fires on the first millisecond rather than 250 ms later.

The exemptions are as deliberate as the rule. `movePointer` stays free for the same reason `SeatUnsupported` exempts it — gliding a ghost cursor over someone's window disturbs nothing, and the refusal belongs on the action. Perception, clipboard, `focusWindow` and `raiseWindow` are free too: looking is never the problem, and focusing the human's window is harmless precisely because the key that follows will be refused. A popup in the transient tree of the focused window counts as the human's window, reusing the descent `popupTransientAt` already does for menu targeting — their open menu is theirs — and the walk runs upward too: a menu takes the keyboard focus of the person using it, so when seat0's focus sits on a popup the guard resolves it to the nearest non-popup ancestor before comparing, because a click into the parent is exactly what dismisses the menu they are in. The release half of a press the agent already delivered is never refused, because a latched button or a stuck Ctrl in someone's window is worse than the press was. And **`ownsCompositor` mode disables the guard outright**: in a nested compositor the agent's input rides seat0, so recency would read back its own events and deadlock it, and there is no human in there to protect.

`setHumanActiveGuardMs(u)` reconfigures it exactly the way `setIdleTimeout` does (`0` disables, otherwise clamped to 100 ms – 60 s), `KWinComputerBackend` pushes its value after each `start()` and tolerates an older plugin that has never heard of the method, and `SYNARA_COMPUTER_HUMAN_ACTIVE_MS` is the operator override with the idle timeout's parsing rules — a typo falls back to the default rather than silently turning the guard off. `stateJson` reports `humanFocusWindowId`, `msSinceHumanInput` (−1 when no real device event has been observed at all, which is not the same as a long quiet period) and `humanActiveGuardMs`, so the rule can be watched from `busctl` instead of inferred. AT-SPI semantic writes get the same refusal server-side, because `setText` reaches the application over the accessibility bus and never touches the plugin's injection paths; it samples a fresh `stateJson` before the action and skips when the fields are absent or the backend owns its compositor. Both tiers speak `computer_human_active` and both are retryable, so the tool surface and the panel copy do not have to know which desktop produced the refusal. Verified live with plugin V16 in the running compositor (2026-08-20): `stateJson` tracked the human's focus window and 2-second input age in real time, and with the guard widened to 60 s a key aimed at the window the human was typing in came back as the named refusal — "their own devices were active 60 ms ago" — with nothing injected.

And a known intermittent resurfaced without regressing: the first Ctrl+Q chord died while KCalc had an agent-opened menu popup and the human's real activation was churning — the borrowed-activation class the V6 fix narrowed but did not close, now with a new suspect (a popup the agent's own click opened, which KWin's popup filter is not holding because no seat0 grab exists). The agent misread it as a stuck Ctrl, recovered by re-clicking the window, and the retry closed it; the plugin held zero keys throughout. Filed as an open sub-case on the hotkey-reliability entry rather than fixed blind.

**Helper-install deferral (2026-08-21).** The audit caught the portal probe contradicting its own "install nothing" rule: `resolveDesktopHelper` — the function that copies a shipped binary into `~/.local/share` — ran inside `probeDesktop()`, which runs at backend construction, i.e. at boot. Resolved in the deferral direction: the boot probe now only _checks_ whether a helper is present (and plans wlroots capabilities away when not); actual resolution — including any install — happens on the backend's throttled re-probe, which also covers the frozen-probe problem (a helper built or installed after boot now appears without a restart). The sentence above about "checksum-verified self-install" stays true of the _resolution_ path; what changed is when it runs.

**Tier 2 could never actually install its own helper (found and fixed 2026-08-26, on Arch/Hyprland).** The pass above records that the wlroots desktop helper "gets the same CI prebuild treatment as the plugin". It got the workflow, but nothing consumed it: `release.yml` referenced `prebuilt` nowhere, `native/computer-desktop-helper/prebuilt/` was populated by no job and committed by nobody, and `desktop-helper-prebuilds.yml` uploaded a `desktop-helper-prebuilt` artifact that a human was expected to unpack by hand. The KWin plugin's artifact was orphaned the same way. So step 3 of `resolveDesktopHelper`'s documented order was dead everywhere, and there was no step 4 at all — `resolveDesktopHelper` can copy a shipped binary but has never been able to build one. Linux Synara runs from source (the AppImage build fails on node-pty's bundled node-gyp), which meant no Linux user could obtain a helper without finding `build.sh` themselves.

Worse than the gap was what it looked like. The helper is also what holds the `wl_display` the registry is read on, so a machine without one produces _no_ global list rather than an empty one — and every plan resolver consulted `probe.waylandGlobals` before reaching `helperBacked()`. On Hyprland, which advertises `zwlr_virtual_pointer_manager_v1`, `zwlr_screencopy_manager_v1`, `zwlr_foreign_toplevel_manager_v1` and `zwlr_data_control_manager_v1`, all four capabilities fell through to their terminal refusals: "this desktop offers neither the wlroots virtual-pointer protocol nor a RemoteDesktop portal" (false), "install xdg-desktop-portal plus your desktop's backend" (already installed), and an instruction to compile PipeWire support for a mechanism that desktop never uses. `helperBacked()`'s carefully written refusal — whose own comment calls this out as "the difference between a user running one script and a user concluding their desktop is unsupported" — was unreachable in production. The correct sentence existed in `probe.gaps`, which `availability()` does not surface.

Three changes. `probe.ts` distinguishes _globals unknown_ from _globals read and empty_: every resolver checks `globalsUnknown()` before its terminal refusal, so a missing helper is reported as a missing helper. GNOME is deliberately exempt on capture, where PipeWire genuinely is the mechanism and `nativeCaptureGap()` already names the helper. `provisioning/desktopHelperProvisioning.ts` gives Tier 2 the lifecycle Tier 1 has had since it shipped — override, stamp-matched install, checksum-verified prebuilt, **build from source**, then a refusal naming every missing package at once rather than one per attempt — and `PortalComputerBackend` finally splits `probeAvailability()` from `availability()` (they were literally the same function, so there was no establishing step for provisioning to hang off), re-probing and swapping its provider set when the answer changes, and comparing plans first so a GNOME desktop holding a live portal grant is not rebuilt into a second consent dialog. An install stamp keyed on a hash of the helper's sources is what makes an _update_ work: the helper reports no version of its own, so without it an upgraded Synara keeps running last release's binary forever. Finally `release.yml` calls both prebuild workflows (now `workflow_call`) and stages their artifacts into the two native roots before packaging, in every job that packages the server; a distribution the matrix cannot build is reported by the called workflow and its users keep the source-build fallback.

Verified live on the reference Hyprland machine: with the helper deleted, all four refusals name it and the settings card offers **Set up**; provisioning compiles it in a few seconds; the plan then resolves `wlroots-virtual-input`, `wlr-screencopy`, `wlr-foreign-toplevel` and `wl-clipboard`, `listWindows()` returns the real window list, and a full-workspace capture comes back correct at 2048×1008. A second run reports `already-current`; changing the helper sources makes the next run recompile. The feature is labelled **Beta** in the sidebar, the settings heading, the composer's mode menu, and the Computer pane.

**Availability is the switch, not a per-chat ritual (2026-08-20, product-owner bar: "like a skill/plugin").** The opt-in model was backwards. Computer control was a per-thread toggle defaulting off (`enableComputerControlForNewChats: false`), and flipping the composer toggle rewrote that global default — so one per-chat "off" silently disabled the tools for every later chat, and a brand-new chat on a working desktop started toolless. An agent asked to drive the desktop in that state could not see a single `computer_*` tool and hand-rolled a D-Bus driver script instead. The fix: whenever the desktop backend is available for a thread, any agent in it may reach for the desktop when asked — the effective per-chat flag now resolves as `draft.enableComputerControl ?? (backendAvailable ? allowInNewChats : false)`, where the repurposed `allowComputerControlInNewChats` machine setting defaults **on** and is a plain opt-out, never auto-flipped by a per-chat choice. A chat's own override still wins in both directions; on a machine with no backend nothing changes (the flag stays off and the composer toggle is hidden). The resolution is one pure function (`resolveEffectiveComputerControl`) so the default-on/off-when-unavailable/override-wins rules are unit-tested, and the effective flag flows unchanged through dispatch → session lease → the `computer:control` capability, so a default-on new chat is granted the capability from its first turn.

Because every available session now carries the capability, the token math flipped too: preloading even the eight act-loop schemas (~3.7k tokens) would tax every chat, including the pure-coding ones that never touch the desktop. So **all** computer tools are now deferred — none carries `anthropic/alwaysLoad`. This is the skill semantics the owner asked for: a chat pays ~0 tokens until an agent first reaches for the desktop, at which point Claude's tool search pulls the whole `computer_*` family in on one query (they share the name segment). The deliberate trade is one search round trip on first desktop use in exchange for charging idle chats nothing; the tools stay in the capability-gated deferred list, so an agent can always find them on request. One boundary could not be made seamless: a provider session that was already running before the capability existed cannot retroactively see tools it was not started with, so the `computerControlChanged` restart path (ProviderCommandReactor) grants them on the session's next start/restart when the flag turns on — a **new** chat always has them from the start; a pre-existing session gains them on its next start.

**Every injected event is delivered exactly once (fixed 2026-08-20, plugin V19).** The pointer-object routing fix (V18) started driving Gecko through direct injection, and exposed an assumption the injection path had been silently making: `clientInputResources()` wrote every event to _every_ `wl_pointer`/`wl_keyboard` resource the client held, which is correct only for single-seat clients. A client holding an input object on both seat0 and the agent seat received each keystroke twice or more — "openai codex" arrived as "oooo pppp eeee nnnn aaaa iiii …". The fix returns exactly the first matching resource: a client processes an event from any one of its resources, so one delivery is sufficient and more is a pure multiplier, never extra reach. Iteration order is stable for the client's life, so enter/key/modifiers/button/axis/leave all land coherently on one object. Verified live (V19): typing "wayland protocol" into Wikipedia's real search box produced exactly that string, its live autocomplete matched, and Enter navigated once — while the human pointer never moved.

**The agent's keystrokes stay on its own target when the human clicks away (2026-08-21, plugin V21).** Direct keyboard injection stamped the target surface with one `wl_keyboard.enter` and streamed keys after it — but that keyboard object lives on the client's seat0, the human's seat, and a `wl_keyboard.key` event names no surface. When the human clicked another window mid-type, seat0 moved the shared object's focus and the agent's remaining keystrokes followed the human's cursor into that window. (Routing the keyboard onto the agent seat instead was tried first and was wrong: Gecko has no usable keyboard object there and dropped every key.) The fix keeps the keyboard on the same path as the pointer and re-stamps the enter on the agent's target before every key, carrying the pre-event held-key state so chords survive — the Wayland twin of macOS posting each event to the target. Verified live (V21): with KWin activation moving seat0's focus to a KWrite window mid-type (`humanFocusWindowId` confirmed it), the agent's second burst still landed in the flatpak Zen input, not KWrite, with no repeats.

**Audit reconciliation (2026-08-22, pre-PR).** The 2026-08-21 deep audit's thirteen high/medium findings were re-verified against the code: ten were already fixed by the benchmark-state commit, each with tests (the fake-backend-off-Linux default, provisioning memoization, portal scroll units, desktop-helper trust/upgrade stamps, chord-release continuation, window-title clamps, AT-SPI frame caps, error-message clamps, tool-layer bounds, portal session/clipboard leaks). The three remainders were closed in this pass: the portal backend now speaks agent space at its boundary exactly as the KWin backend does — shared shift helpers in `computerGeometry.ts`, window bounds and capture regions translated out, pointer coordinates and capture requests translated in — so negative-origin multi-monitor layouts are clickable on GNOME/wlroots too; the KWin plugin proxy is pinned to the owner's unique bus name at connect, so a squatter or stale generation taking the well-known name after the ownership check can never receive input or serve captures; and `install-and-load.sh` compares the running plugin's reported build id against the header its own build just compiled, failing loudly when another generation still owns the service. One item stays open by design: prebuilt container images and CI actions are digest/SHA-pinned (test-enforced), but manifest _signing_ needs a key in the upstream repo's CI and is the maintainer's call — the manifests ship inside the app package, so the residual exposure is local tampering, not network interception.

**Upstream codex-review pass (2026-08-24).** Eight findings from the upstream PR's automated review, each verified against the code before any change. The one reversal of a recorded decision: `allowComputerControlInNewChats` now defaults **off**, undoing the 2026-08-20 "like a skill" default-on — the PR's own stated posture is "opt-in per thread and never a default capability", and default-on granted even the approval-free read-only tools (screenshots, window enumeration) to every new chat; the machine setting, the per-chat override, and the never-auto-flipped rule are all unchanged. The live-upgrade story the docs promised is now real end to end: the service layer no longer freezes `supported` to the boot probe's verdict (a real Linux backend stays routed through the manager, so a helper installed after boot appears without a restart), the portal backend's establishing read invokes `resolveDesktopHelper` — the deferral entry above had left it defined but uncalled — and a reprobe upgrade now merges per slot, keeping live providers with their sessions and consent, disposing the fresh duplicates, and rebuilding the capability set and seat arbiter from the merged set (the manager reads capabilities live rather than caching construction's answer). A dismissed portal consent dialog is no longer terminal: the denial still latches and still refuses without re-prompting, but health reports `consent-denied`, availability carries the reason, and the Computer panel's blocked state offers "Ask for permission again" (`computer.resetConsent`, deliberately absent from the agent tool surface) — one reset buys exactly one more ask. The GNOME capture refusal stops promising a rebuild that changes nothing (no PipeWire receiver exists anywhere in the stack) and names the nested-window desktop as what works today. Turbo's strict env pass-through gained the computer-control variables, whose absence silently ignored `SYNARA_COMPUTER_BACKEND` and the nested lanes under `bun run dev`. And a bare `window_id` is a real scroll target again — the window itself, at its own point — while the control-less refusal stays for the semantic writes.

**The action-observation budget is 1536px, not the 1024 the requirements pass recorded (raised 2026-08-21).** The tighter cap saved tokens but cost the precision needed to read a form or aim at a small field, and a live run showed the cost coming back the wrong way: mis-aimed clicks and extra re-screenshots were slower and more expensive than the shot they shrank. The cap now matches the height of a typical browser or editor window, so those come back at full resolution and only a genuinely large capture is scaled. The token saving that mattered stays: the byte-identical dedupe never resends an unchanged frame, and `computer_screenshot` still zooms further on demand.

Tier 3 feasibility (probed live 2026-08-16). A nested `kwin_wayland --virtual --socket <name>` under `dbus-run-session` is a working Tier 3: it boots headless in ~2 s with no DRM or session dependencies, the installed Synara plugin comes up inside it (`healthJson` ok; since 2026-08-19 it reports `ownsCompositor: true` and drives seat0 through a `KWin::InputDevice` rather than creating a second seat — see the seat-reach entry above), a real Qt app launched with `WAYLAND_DISPLAY=<name>` appears in `windowsJson` with full metadata, and `start` opens an input session with the pointer parked at screen center. `--width`/`--height` set the virtual output, so CI can pick its own geometry. Two findings for the eventual harness: (1) KWin auto-loads every installed plugin version at startup and the oldest registrant wins the `org.synara.ComputerUse` bus name, shadowing newer builds — an explicit `LoadPlugin` of the newest then returns `false` because it is already loaded but name-shadowed. The live session avoids this because install-and-load.sh unloads stale versions first; a Tier 3 harness must do the same (or the plugin metadata should set `EnabledByDefault=false` so only explicit loads happen — a plugin-side change for the next sudo install). (2) CI needs the plugin built against its own KWin, so the runner image must carry `kwin-devel` and run the existing installer, which already stamps and gates on the KWin version.

Tier 3 nested backend (shipped, `apps/server/src/computer/nestedKWinSession.ts`). `SYNARA_COMPUTER_NESTED=1` makes the service layer boot a private session bus (`dbus-daemon --session --print-address=1 --nofork`) plus `kwin_wayland --virtual --xwayland --no-global-shortcuts` on it (`--xwayland` because X11 clients are one of the two families the dedicated seat cannot reach, and this session is where they are meant to be driven); `SYNARA_COMPUTER_NESTED=window` boots the same session in windowed mode — `--virtual` is dropped and the host `WAYLAND_DISPLAY` is kept, so the nested compositor maps as an ordinary window on the human's desktop (an isolated agent desktop in a window; this is Tier 2 Phase A, and it refuses to start with an actionable error when no host `WAYLAND_DISPLAY` exists rather than falling back to virtual). Either way the geometry comes from `SYNARA_COMPUTER_NESTED_SIZE=WxH` (default 1920×1080) and the service layer points the ordinary `KWinComputerBackend` at the private bus through a new `busAddress` option — nothing else about the backend changes. The compositor's environment always drops `DISPLAY`, and in virtual mode also `WAYLAND_DISPLAY`, so a virtual compositor can never attach to the session the user is sitting in (windowed mode keeps `WAYLAND_DISPLAY` — attaching to the host session as a client window is its purpose); and launched apps get the nested `WAYLAND_DISPLAY`, the private `DBUS_SESSION_BUS_ADDRESS`, `QT_QPA_PLATFORM=wayland`, and the nested Xwayland's `DISPLAY` (read back from the plugin's `healthJson`, and always set — empty when unknown — because a child inherits the server's environment underneath, so merely omitting it would leave the human's `:0` in place and open an X11 client on their screen). Session setup resolves the plugin-shadowing finding above by unloading every loaded Synara plugin id before loading the newest installed one (KWin's `UnloadPlugin` answers `b` on older builds and void on newer; both are tolerated). There is deliberately no fallback in either direction — a failed nested boot yields a backend whose availability names the failed step (missing binary, uninstalled plugin, name never taken, compositor exit with its stderr tail), and a broken real desktop never silently swaps in an invisible nested one. A nested compositor is also not restarted if it crashes: the private bus outlives it, KWin's names vanish, and health reports `reconnecting` with climbing failures — verified by killing the compositor in the integration test. Clipboard works as-is because wl-clipboard follows `WAYLAND_DISPLAY` into the nested seat; AT-SPI perception defaults off because the a11y registry is per-user, not per-bus, so inside a desktop session the helper would either fail (SELinux blocks the private bus from activating a registry) or read the human's real desktop into the nested window list — `SYNARA_COMPUTER_NESTED_ATSPI=1` opts back in for CI containers that run a registry on the nested bus. End-to-end coverage lives behind `SYNARA_NESTED_KWIN_TEST=1` (boot, geometry, listing, launch, capture, clipboard round-trip, crash health) with always-on unit tests for the pure parts.

**Shared-seat backend removed (2026-08-29).** The user's rule, restated verbatim: nothing may stay that does not give the agent its own computer or its own cursor — "it should never take control of my mouse." Disabling the portal backend (2026-08-26) left it in the tree as dead code with live plumbing threaded through everything else: a `computer.resetConsent` RPC and `awaiting-consent`/`consent-denied` health states for a permission dialog only the portal ever showed, a `sharedSeat` capability every remaining backend answered `false`, a `seat` health field only the arbiter ever filled, and a CI job building a helper nobody could select. All of it is deleted: `apps/server/src/computer/portal/`, `native/computer-desktop-helper/`, `native/gnome-shell-extension/`, `sharedSeatArbiter.ts`, the helper provisioning modules (`desktopHelperProvisioning`, `installStamp`, `toolchain`), `desktop-helper-prebuilds.yml` and its release-workflow job and staging steps, the `SYNARA_NESTED_WLROOTS_TEST` env pass-through, and the consent/`sharedSeat`/seat-health contract surface end to end (contracts → server → web). The two constants the KWin/Hyprland backends shared with the arbiter — `HUMAN_ACTIVE_REFUSAL` and `DEFAULT_HUMAN_ACTIVE_THRESHOLD_MS` — now live in `humanActivity.ts`, because the human-active guard is a plugin feature (do not type into the window the human is working in) and has nothing to do with seat sharing. What remains is exactly the set that satisfies the rule: the KWin plugin and its Hyprland twin (a dedicated seat and ghost cursor on the real desktop) and the headless nested KWin desktop (its own computer). A GNOME or wlroots desktop therefore gets the nested desktop and nothing else; the PR description's "GNOME and wlroots desktops" support is nested-only from here.

**Agent clicks were swallowed once the human hovered another window of the same client (fixed 2026-09-02, Hyprland plugin).** Reproduced with Zen (one process, two windows): every agent click on window A landed until the human moved their real pointer into window B; from then on every click on A — page buttons, the address bar — was dropped while keys kept arriving. The mechanism is the pointer twin of the V21 keyboard problem. Direct injection writes to the client's own `wl_pointer`, and that object is shared with the human's seat: the client keeps exactly one "entered" surface on it, whichever `wl_pointer.enter` it heard last from either of us. `motion` and `button` name no surface, so once the seat entered B, the client routed the agent's events (still aimed at A by the plugin's own bookkeeping, which saw the same surface and skipped the enter) to B, and once the seat left B, to nothing. The keyboard path had already been given a re-stamp before every key; the pointer path had nothing, and nothing in the plugin observed seat focus at all. The fix subscribes to `CSeatManager::m_events.pointerFocusChange` (emitted after the seat has sent its own leave/enter and updated `m_state.pointerFocus`), remembers the seat's previous focus itself because the signal carries no payload, and when the seat's old or new focus belongs to the `wl_client` the agent is entered on, drops the agent's enter without sending a leave (the enter the client now believes in is the seat's, not ours to revoke — the rule `directPointerLeave` already followed) after releasing any agent-held buttons, so nothing stays pressed on a surface the agent can no longer address. The next `updatePointerFocus()` then sees a different surface and sends a fresh enter and motion before the button, on the ordinary motion path, so hover state on the target is untouched by focus changes between other clients. Verified in a disposable nested Hyprland 0.56.2 (own D-Bus session, plugin loaded by path) against a two-window GTK4 client plus a separate terminal client, driving the nested seat with `movecursor`: agent click on A landed; the seat entered B and left onto the terminal; the agent's next click on A landed again, with no events in B; a press held across that excursion was released (`pressedButtonCount` 1 → 0) and the next click was a clean press; hover enter/leave inside A still tracked agent motion; and typing into A's entry continued across the same excursion. The pre-fix build, swapped into the same session, dropped step (c) both with and without prior agent motion. Remaining risks: a client holding more than one `wl_pointer` on the seat is re-entered on the first resource only (the exactly-once rule of V19); a popup or subsurface of the target counts as the same client, so an agent hover over a dropdown is invalidated by the human entering the parent window and re-entered on the next motion, which is the intended behaviour but costs one extra enter; and a seat focus change during an active drag is refused by the compositor before the signal fires, so a drag the human starts in a sibling window is not observed until it ends.
